# Общее — загрузка счетов

## Зачем всё это

Приходят счета от поставщиков в российских рублях. Сейчас порядок такой: сначала руками завести товары в 1С, потом сделать документ установки цен. Долго и неудобно, особенно в дороге.

Хотим наоборот: **счёт разбирается на сайте с телефона**, товары и цены готовятся здесь, а в 1С всё уходит одной командой, когда владелец нажмёт кнопку.

## Обстановка

- **Конфигурация 1С:** УНФ 3
- **База:** стоит на сервере с постоянным доступом
- **Связь с 1С:** OData (стандартный интерфейс платформы, включается галочкой при публикации базы — обработки писать не нужно)
- **Валюта счетов:** российский рубль, пересчёт в белорусский по курсу, который владелец вводит вручную

## Почему OData, а не обработка

Владелец не пишет и не хочет писать обработки в 1С. У платформы 8.3 есть встроенный интерфейс OData — сайт обращается к 1С напрямую, как к базе данных. От 1С нужна только галочка в публикации и отдельный пользователь с правами.

Рассматривали также типовой «Обмен с сайтом» (CommerceML) и обмен файлами — оба отпали: первый слишком жёсткий по формату, второй не работает в реальном времени.

## Обязательные реквизиты номенклатуры в УНФ 3

Без них 1С не примет новый товар:

- Артикул
- Штрихкод (если есть)
- Наименование
- Наименование полное (для печати)
- Вес брутто
- **Способ списания — FIFO** (всегда)
- **Ставка НДС — без НДС**
- Единица измерения
- Вид номенклатуры
- Группа

## Найденная проблема: артикулы не уникальны

Проверка каталога на реальных данных:

- Всего товаров: **20 632**
- Связано с 1С по идентификатору: **20 628**
- Артикулов кириллицей: **5 479**
- Артикулов латиницей: **8 824**
- Смешанных: **65**

**Главное:** если сопоставлять по артикулу вслепую, **3 686 товаров схлопываются в 1 159 групп**.

Причина не в раскладке, а в том, что артикул в каталоге не уникален. Пример: `HE-IR217` — это **18 разных карточек**, отличающихся только цветом (белый мрамор, белый/зелёный, белый/розовый, зелёный нефрит и так далее).

**Вывод:** автоматически проставлять цену по артикулу нельзя. Неоднозначность разрешает владелец вручную — через выбор из списка кандидатов.

## Сквозные решения

1. **Артикулы не трогаем никогда.** Ни при поиске, ни при создании карточки. Записываем ровно так, как в счёте или как уже есть в каталоге — буква в букву.
2. **Нормализация кириллицы/латиницы — только внутри сравнения.** Как невидимая линейка: сопоставили нормализованные, а записали оригинал.
3. **Поиск идёт только по артикулу.** Галочка «искать в наименованиях» остаётся ручной, как в пакетном вводе сейчас.
4. **В 1С ничего не уходит без команды владельца.** Все этапы до пятого живут только на сайте.
5. **Новые товары при разборе счёта — полноценные карточки**, не временные товары. Ветка временных остаётся для заявок.

## Что переиспользуем

**Пакетный ввод из заявок** (`backend/wholesale-orders-bulk-resolve/` + `src/pages/shared/BulkPastePage.tsx`) уже умеет главное: принимает список артикулов, раскладывает результат на «нашёл один» / «нашёл несколько» / «не нашёл», показывает кандидатов на выбор, считает цены по правилам фирмы.

Второй этап строим на нём — не переписываем, а дорабатываем.
