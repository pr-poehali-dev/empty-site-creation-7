# Подключение к 1С через OData

Прямой доступ к справочникам и документам 1С по обычным HTTP-запросам. Обработка `.epf` для этого не нужна: сайт сам читает и пишет данные в базу.

В 1С этот механизм называется двумя именами — **стандартный интерфейс OData** и **автоматический REST-сервис**. Это одно и то же.

## Кто что включает

| Что | Где | Кто делает |
|---|---|---|
| Публикация OData на веб-сервере | ЛК Е-Офис24 | хостер (Е-Офис24) |
| Состав объектов (какие справочники отдавать) | режим Предприятия, обработка | мы сами |
| Логин и пароль доступа | та же обработка, вкладка «Авторизация» | мы сами |

Публикацию мы включить не можем — это делает Е-Офис24 по заявке. Состав объектов настраивается без Конфигуратора и без прав на сервер.

## Как открыть настройку состава

Режим Предприятия, под пользователем с полными правами. Главное меню → **Файл → Открыть** не подойдёт, нужен переход по внутреннему адресу:

```
e1cib/app/Обработка.НастройкаСтандартногоИнтерфейсаOData
```

При работе через браузер — добавить к адресу базы `#e1cib/app/Обработка.НастройкаСтандартногоИнтерфейсаOData`.

Откроется окно **«Настройка автоматического REST-сервиса»** с двумя вкладками: «Авторизация» и «Состав».

## Вкладка «Авторизация»

Галочка **«Создать для использования автоматического REST-сервиса отдельные имя пользователя и пароль»** создаёт служебного пользователя (по умолчанию `odata.user`), который не может зайти в саму 1С — только читать и писать данные через сервис.

Если доступ уже настроен под существующим пользователем — галочку не трогать.

Пароль в код сайта не пишется. Он хранится в секретах проекта.

## Вкладка «Состав»

Дерево объектов конфигурации с галочками. Отмечены для работы сайта:

**Справочники:** Контрагенты, Договоры контрагентов, Номенклатура, Организации, Склады, Страны мира, Номера таможенных деклараций, Классификатор единиц измерения

**Документы:** Реализация товаров услуг, Поступление товаров услуг

**Планы счетов:** Хозрасчетный

**Регистры сведений:** Счета учета номенклатуры, Счета учета расчетов с контрагентами

**Перечисления:** Ставки НДС

Кнопку **«Загрузить метаданные»** не трогать — она для другой задачи.

После отметок — **«Сохранить и закрыть»**.

### Окно «Зависимости объекта»

При установке галочки 1С показывает список объектов, на которые ссылаются реквизиты выбранного. Нужно нажимать **«Да»**.

Пометка **«(не используется)»** у строк — нормально. Реквизит входит в состав типа, но в этой базе не заполняется. Платформа всё равно требует разрешить весь состав типа, иначе основной объект не отдастся.

Разрешение зависимостей не открывает данные наружу — доступ всё равно только по логину и паролю.

## Грабли, на которые уже наступили

**Метаданные открываются, а объект не находится.** Запрос `$metadata` отдаёт XML, а `Catalog_Контрагенты` возвращает «Сущность не найдена». Значит публикация работает, но объект не отмечен в составе. Лечится вкладкой «Состав», а не правами.

**Файл .vrd не содержит состав объектов.** В нём только строка `<standardOdata enable="true"/>` — включение сервиса. Список справочников и документов хранится внутри базы. Передать настройку хостеру файлом нельзя.

**Длинный фильтр с «или» возвращает пустоту.** Запрос вида `Номер eq 'A' or Номер eq 'B' or ...` на два десятка условий отдаёт ноль совпадений — без ошибки, просто пустой список. Тот же самый номер, запрошенный отдельно, находится сразу. Пачками в этой базе не спрашиваем, только по одному.

**Счета учёта.** Без плана счетов Хозрасчетный документы реализации и поступления не проведутся. Регистры «Счета учета номенклатуры» и «Счета учета расчетов с контрагентами» нужны, чтобы счета подставлялись автоматически, как в интерфейсе 1С. Без них счёт придётся указывать в каждой строке документа вручную.

## Тесты после настройки

Проверять по порядку — каждый следующий имеет смысл только если предыдущий прошёл. Базовый адрес: `https://<адрес базы>/odata/standard.odata/`

Ко всем запросам добавлять `?$format=json`, иначе 1С отдаёт XML.

### 1. Сервис отвечает

```
/odata/standard.odata/$metadata
```

Ожидаем XML со схемой. Если просит логин — ввести служебного пользователя. Если 404 — публикация не включена, вопрос к Е-Офис24.

### 2. Состав объектов виден

В ответе `$metadata` поиском (Ctrl+F) найти `EntitySet`. Каждое совпадение — один опубликованный объект. Должны найтись `Catalog_Контрагенты`, `Document_РеализацияТоваровУслуг`, `ChartOfAccounts_Хозрасчетный`.

### 3. Чтение справочника

```
/odata/standard.odata/Catalog_Контрагенты?$top=1&$format=json
```

Ожидаем JSON с одним контрагентом: поля `Ref_Key`, `Description`, `ИНН`.

`Ref_Key` — это внутренний идентификатор объекта в 1С. По нему сайт связывает свои карточки с 1С.

### 4. Поиск по условию

```
/odata/standard.odata/Catalog_Контрагенты?$filter=ИНН eq '7701234567'&$format=json
```

Ожидаем одного контрагента или пустой массив. Проверяет, что фильтры работают — на них построен весь поиск.

### 5. Чтение номенклатуры с ценой единицы

```
/odata/standard.odata/Catalog_Номенклатура?$top=5&$format=json
```

Смотрим, что приходят артикул, единица измерения, ставка НДС.

### 6. Чтение документа с таблицей товаров

```
/odata/standard.odata/Document_РеализацияТоваровУслуг?$top=1&$expand=Товары&$format=json
```

`$expand=Товары` подтягивает табличную часть. Ожидаем документ с массивом строк внутри. Если таблица не пришла — проверить имя табличной части в `$metadata`.

### 7. План счетов

```
/odata/standard.odata/ChartOfAccounts_Хозрасчетный?$filter=Code eq '41.01'&$format=json
```

Ожидаем счёт «Товары на складах».

### 8. Регистр счетов учёта

```
/odata/standard.odata/InformationRegister_СчетаУчетаНоменклатуры?$top=3&$format=json
```

Ожидаем записи с полями счетов доходов, расходов, НДС.

### 9. Запись данных

Самый важный тест — до него всё было только чтением.

POST на `/odata/standard.odata/Catalog_Контрагенты?$format=json` с телом:

```json
{
  "Description": "Тестовый контрагент Юра",
  "ИНН": "0000000000"
}
```

Ожидаем ответ 201 с `Ref_Key` созданного элемента. Если 403 — у служебного пользователя нет прав на запись.

### 10. Уборка за тестом

Созданного контрагента пометить на удаление — PATCH на `/odata/standard.odata/Catalog_Контрагенты(guid'<Ref_Key>')` с телом `{"DeletionMark": true}`.

Полностью удалять через OData нельзя, только помечать. Физическое удаление — через «Удаление помеченных объектов» в 1С.

## Что нужно для подключения сайта

1. Полный адрес базы — то, что в браузере до `/odata/`
2. Имя служебного пользователя
3. Пароль

Эти три значения кладутся в секреты проекта, в коде их нет.

### Выводы

**Запись работает.** Документы создаются непроведёнными, со строками товаров и рассчитанным НДС.

**Прав на удаление у служебного пользователя нет.** Нужно добавить профиль в 1С: Администрирование → Настройки пользователей и прав. Пока тестовые документы убираются вручную.

**Таймаут функции — 30 секунд.** Пять секунд не хватало: создание поступления и реализации в УНФ идёт дольше из-за внутренних проверок.

**Ошибки в адресе.** Кириллица в пути (`Catalog_Номенклатура`) должна кодироваться, иначе запрос падает ещё до отправки.

**Проверка связи** делается запросом к корню сервиса, а не к `$metadata` — схема слишком тяжёлая, функция не успевала её прочитать.

### Важное про OData

OData пишет в базу напрямую, в обход форм 1С. Автоматика не срабатывает: суммы, НДС, счета учёта, подстановка договора — ничего не заполнится само. Что отправили, то и легло.

Значит, все расчёты делаются на стороне сайта и передаются готовыми числами.

### Главные грабли: документ создался пустым

Счёт 0000-000086 записался как положено — номер, дата, входящий номер поставщика. Товаров внутри не оказалось ни одного.

Причина: строки отправлялись в табличную часть с именем `Запасы`. В нашей конфигурации она называется иначе — на форме документа видно «Товары и услуги».

**Самое опасное — реакция 1С.** Она не отказала и не предупредила. Получила незнакомое имя реквизита, молча его выбросила и вернула ответ «создано» с новым номером. Со стороны сайта всё выглядело успехом.

Вывод на будущее: **OData не проверяет имена реквизитов**. Опечатка или неверное имя — это не ошибка, а тишина. Ответ «создано» сам по себе ничего не доказывает: надо смотреть, что реально легло внутрь.

### Как починили

**Функция определяет имена сама.** Перед созданием документа она читает один существующий документ того же вида из этой же базы и смотрит, как на самом деле называется таблица товаров и какие колонки внутри неё. Отправляет по фактическим именам, а не по заранее зашитым.

Если подходящей таблицы не нашлось — документ не создаётся, а возвращается понятная ошибка со списком доступных реквизитов. Пустых документов больше не появляется.

**Проверка после записи.** Функция считает, сколько строк вернула 1С, и сверяет сумму с отправленной. Ноль строк — результат считается неудачным, даже если 1С ответила «создано». Расхождение в сумме — предупреждение в отчёте.

В результатах на странице теперь видно, в какую именно таблицу легли строки.

### НДС

Ставка выбирается в шапке страницы: **22%, 10%, 5%, 0%, Без НДС**. По умолчанию 22%, выбор запоминается в браузере. Ставка одна на весь документ; если понадобятся разные по строкам — добавим колонку в файл.

**Налог считается в сумме.** Цены в счетах поставщиков идут с налогом внутри, поэтому цена из файла остаётся неизменной, а НДС выделяется изнутри:

```
НДС = сумма × ставка ÷ (100 + ставка)
```

При 22% из 1220 рублей получается 220 рублей налога. Для «Без НДС» и 0% налог нулевой.

**Признак «НДС в сумме» функция ищет сама** — в разных конфигурациях реквизит зовётся по-разному (`СуммаВключаетНДС`, `ЦенаВключаетНДС` и другие). Если такого реквизита в документе нет, в отчёте появится предупреждение: 1С может посчитать налог сверху.

### Правила файла для создания документов

Семь колонок: артикул, наименование, количество, цена, страна происхождения, номер ГТД, номер РНПТ.

Последние три — для поступления и реализации.

Организация, склад и ставка НДС берутся из настроек страницы, не из файла.

Контрагент не заполняется. От поставщика переносятся только номер и дата счёта.
## Сверка номеров ГТД (сентябрь 2026)

### Что было сломано

Накладная на 815 номеров ГТД. Сверка показывала: в базе найдено 0, новых 815 — при том, что все эти номера в справочнике есть. Ошибки 1С при этом не выдавала, просто пустой ответ.

Причина: номера спрашивались пачками по 25 штук одним фильтром через «или». На такой запрос база отвечает пустым списком. Один номер, спрошенный отдельно, находился мгновенно.

### Как починили

Поиск переведён на одиночные запросы: один номер — один запрос, ровно тот способ, который работает безотказно. Чтобы это не тянулось вечно, запросы идут параллельно в 8 потоков.

Порция в 40 номеров проверяется примерно за 3 секунды. Все 815 — около минуты, с живым счётчиком на экране.

Ответ 1С теперь всегда показывается пользователю. Раньше отказ молча превращался в «не найдено», и было не понять, номера нет или база не ответила.

### Правило на будущее

Фильтры с перечислением через «или» не использовать. Спрашивать по одному, параллелить потоками.

## Таймаут при создании документа

### Что было сломано

После успешной сверки кнопка «Создать поступление в 1С» выдавала «1С отказала — Failed to fetch».

Причина не в 1С. Создание документа заново искало все 815 номеров — около минуты, а на одну операцию отведено 30 секунд. Операция обрывалась по времени, и обрыв выглядел как отказ базы.

### Как починили

Номера, найденные при сверке, теперь запоминаются вместе со ссылками на записи справочника и передаются в создание документа. Повторный поиск не нужен — документ собирается за секунды. Если какой-то ссылки не хватило, доискивается только она одна.

### Правило на будущее

Одну и ту же работу дважды не делать. Долгий перебор дробить на порции: каждая отвечает сразу, а перебор ведёт страница со счётчиком. Функция, которая ждёт окончания всего списка, упрётся в лимит времени.

## Чего OData не умеет

**Ввод «на основании» недоступен.** Через OData можно читать, создавать, изменять, удалять и проводить документы. Штатные механизмы заполнения — те самые кнопки «Создать на основании» — живут внутри конфигурации и наружу не публикуются.

Значит, реализацию или счёт покупателю из поступления OData сам не соберёт. Два пути:

- собрать документ на нашей стороне: прочитать поступление, перенести шапку и товары, подставить свои цены. Доработок 1С не требует;
- заказать программисту 1С HTTP-сервис, который внутри вызывает родную обработку заполнения. Работает штатная логика, но нужна доработка конфигурации.

Для счёта и реализации обычно хватает первого пути: переносятся номенклатура, количество, склад и организация, а цены всё равно ставятся продажные, а не закупочные.
