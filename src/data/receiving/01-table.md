# Шаг 1. Таблица приёмки

## Задача шага

Создать в базе хранилище, куда лягут все строки из файлов поставщиков. Это основа всего: из неё идёт приёмка, из неё собираются красивые наименования, по ней считаются остатки на складах.

Одна строка таблицы = **одна физическая единица товара**. Не позиция каталога, а конкретный чайник с конкретным штрихкодом.

## Три таблицы

**Поставщики приёмки** — название (М-Видео и далее другие). К поставщику привязываются схемы разбора файлов и фильтры в сводках.

**Журнал загрузок** — каждая загрузка файла отдельной записью: имя файла, поставщик, кто грузил, когда, сколько строк прочитано, добавлено, пропущено как повторы. Даёт историю партий и возможность откатить неудачную загрузку целиком.

**Единицы товара** — главная таблица, описана ниже.

## Поля взятия в работу

Заполняются в момент, когда сотрудник впервые берёт товар — до проверки:

| Поле | Что это |
|---|---|
| Упаковка | Есть или нет |
| Вес для накладной | Пишется **сразу** после ответа об упаковке |
| Заводской штрихкод | Тот, что на самом товаре |
| Второй заводской штрихкод | Задел на будущее, пока не используется |

### Вес пишется сразу

Ответил сотрудник про упаковку — в ту же секунду в карточку ложится вес: брутто при упаковке, нетто без неё. Если в файле только один вес, вопрос задаём всё равно, а записываем тот, что есть.

Ждать окончания проверки незачем — данные уже известны.

### Заводской штрихкод спрашиваем только при упаковке

Заводской код печатают **на коробке**. Нет коробки — сканировать физически нечего, и шаг пропускается: сразу к выбору исхода.

То есть код спрашивается при двух условиях сразу: упаковка есть **и** кода ещё нет в карточке. На вес это не влияет — вопрос об упаковке задаётся всегда, он нужен и для накладной.

### Заводской штрихкод размножается по однофамильцам

Сотрудник отсканировал заводской код один раз — система проставляет его **всем единицам с тем же техническим наименованием**: и тем, что уже лежат в таблице, и тем, что придут в следующих файлах. Одно сканирование закрывает всю модель.

Кнопка «Штрихкод повреждён» просто пропускает вопрос, ничего не записывая. На следующем таком же товаре наклейка будет целой — пикнул, и модель закрыта навсегда.

**Зачем это нужно.** Когда товар уходит на склад готовой продукции, этикетка поставщика снимается — покупателю она ни к чему. Дальше учёт и отпуск идут по заводскому штрихкоду: пикнули товар на продаже, и каталог сразу понимает, что перед ним. Без заводского кода в карточке такое сканирование невозможно.

## Поля проверки

Пустые до тех пор, пока мастер не проверит товар. Заполняются на шаге 6, **по каждой единице отдельно**:

| Поле | Что это |
|---|---|
| Исход проверки | На продажу / на протирку / не работает / утиль |
| Заявленный дефект подтвердился | Да / нет |
| Новый дефект | Да / нет |
| Описание нового дефекта | Текст от мастера |
| Кто проверял | Сотрудник |
| Когда проверял | Дата и время |
| Номер дневной приёмки | К какой приёмке относится |

Зачем это в карточке каждой единицы: поставщик заявил товар рабочим. Значит ему предъявляем — списком по техническим наименованиям, где по каждой единице видно, что заявляли и что оказалось на деле.

## Защита от повторной загрузки

Штрихкод поставщика в таблице уникален. Если в новом файле встретится штрихкод, который уже есть, строка **не создаётся заново** — система покажет предупреждение и посчитает такие строки отдельно. Так один и тот же файл, загруженный дважды, не раздует таблицу.

Заводской штрихкод уникальным **не делаем** — он один на сотни экземпляров, это нормально.

## Скорость

Файл на 17 тысяч строк, а их будет много — таблица вырастет до сотен тысяч. Чтобы поиск не тормозил на телефоне, заложен быстрый доступ по:

- заводскому штрихкоду — по нему пикают на продаже, должно летать
- номеру заказ-наряда
- техническому наименованию
- складу
- связке «товарная группа + бренд + модель» — для сборки красивых имён на шаге 4
- загрузке — чтобы откатить партию
- сотруднику и дате проверки — для сводок
